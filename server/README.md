# Cafe Menu SaaS — Backend (этап 1: БД, миграции, авторизация, tenant isolation)

Это **не весь проект**, а первый слой — фундамент, на котором будет строиться
всё остальное (админка, клиентское меню, дизайн, статистика и т.д.). Ниже —
честный список того, что реально сделано и проверено, и что ещё нет.

## Стек

Node.js + Express + PostgreSQL (`pg`, без ORM), JWT-авторизация, bcryptjs
(чистый JS, без нативной сборки — чтобы не повторить проблему с
better-sqlite3 на Windows из прошлых проектов), Zod для валидации.

## Запуск локально

```bash
cd server
cp .env.example .env
# отредактируйте .env: DATABASE_URL, JWT-секреты, SUPERADMIN_*

npm install
npm run migrate          # применяет все миграции
npm run seed:superadmin  # создаёт первого Super Admin из .env
npm start                # http://localhost:4000
```

Проверка: `curl http://localhost:4000/health` → `{"status":"ok"}`

## Переменные окружения (.env)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_SSL` | `true` для облачных БД (Neon/Render/RDS) |
| `PORT` | порт API (по умолчанию 4000) |
| `CLIENT_ORIGIN` | разрешённые origin для CORS, через запятую |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | секреты для токенов, ≥32 симв. в проде |
| `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` | время жизни токенов (например `15m`, `30d`) |
| `SUPERADMIN_PHONE` / `SUPERADMIN_PASSWORD` / `SUPERADMIN_FIRST_NAME` / `SUPERADMIN_LAST_NAME` | данные для `npm run seed:superadmin` |
| `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_MINUTES` | брутфорс-защита логина |

## Команды миграций

```bash
npm run migrate          # применить все новые миграции
npm run migrate:status   # какие применены / ожидают
npm run migrate:down     # откатить последнюю (если есть файл *.down.sql)
```

Миграции лежат в `src/db/migrations/*.sql`, применяются по порядку номеров,
каждая — в своей транзакции, факт применения фиксируется в таблице
`schema_migrations`. Повторный запуск `migrate` безопасен (ничего не сломает).

## Создание первого Super Admin

```bash
npm run seed:superadmin
```

Берёт данные из `SUPERADMIN_*` в `.env`. Если пользователь с таким телефоном
уже есть — ничего не делает (безопасно перезапускать).

## Архитектура авторизации и tenant isolation

- **JWT access-токен** (короткоживущий, в заголовке `Authorization: Bearer`) +
  **refresh-токен** (случайная строка, в БД хранится только её SHA-256 хэш,
  при каждом обновлении — ротация: старый токен сразу отзывается).
- **Пароли** — bcryptjs, 12 раундов, никогда не хранятся в открытом виде.
- **Tenant isolation** — middleware `resolveCafeAccess`:
  - для **Admin** — `cafeId` всегда вычисляется на сервере из его же
    аккаунта (его кафе), клиентский `cafeId` из тела/параметров запроса
    полностью игнорируется;
  - для **Super Admin** — `cafeId` берётся из `:cafeId` в URL, кафе
    проверяется на существование.
  - Дополнительно каждый SQL-запрос в репозиториях сам фильтрует по
    `cafe_id` (двойная защита — не "получить и сверить", а "получить
    только своё").
- **Брутфорс-защита** — через таблицу `login_attempts` в БД (не in-memory),
  чтобы работало и после перезапуска процесса, и при нескольких инстансах.
- **Блокировка админа Super Admin'ом действует мгновенно** — даже с уже
  выданным токеном, т.к. статус пользователя проверяется на каждый запрос.

## Реально протестированные сценарии (не просто "должно работать")

Прогонялось вживую на локальном PostgreSQL внутри песочницы:

1. Применение всех 11 миграций → 25 таблиц, повторный запуск ничего не ломает
2. Регистрация Admin создаёт пользователя + кафе + настройки + 7 дней рабочих
   часов + QR-ссылку одной транзакцией
3. Логин Super Admin и Admin, `/me`
4. **Tenant isolation**: Admin A создаёт категорию → Admin B видит пустой
   список → Admin B пытается `PATCH`/`DELETE` категорию Admin A по её id
   напрямую → оба раза `404`, категория Admin A не изменена
5. Admin не может достучаться до Super Admin-роутов (`403`)
6. Super Admin видит все кафе/админов, может создать ресурс в чужом кафе
   через `/api/superadmin/cafes/:cafeId/...`
7. Блокировка админа Super Admin'ом → у админа мгновенно `403` даже со
   старым токеном, повторный логин тоже `403`; разблокировка возвращает доступ
8. 6 подряд неверных паролей → на 6-й попытке `429` (лимит — 5)
9. Ротация refresh-токена: после `refresh` старый токен повторно
   использовать нельзя (`401`)
10. Уникальность телефона на регистрации, каскадное удаление связанных
    записей при удалении кафе/пользователя — проверено через `TRUNCATE ... CASCADE`
11. Express не отдаёт стек-трейсы наружу; `helmet` и `CORS` подключены

## Этап 2: CRUD для блюд, рекламы, галереи, контактов, дизайна — реально протестировано

Прогонялось вживую поверх этапа 1 (тот же локальный PostgreSQL):

- **Блюда**: создание с ценой/категорией/описанием, редактирование, удаление;
  атрибуты (вес/калории/аллергены/острота/время готовки/состав) с
  индивидуальным ВКЛ/ВЫКЛ на каждый; перевод на английский; метки
  (популярное/острое/...); drag&drop reorder
- **Блоки меню**: создание, привязка списка блюд (`PUT .../dishes`),
  дублирование (копирует и название, и состав блюд), reorder
- **Реклама, галерея, контакты**: полный CRUD + reorder на каждом;
  валидация типа контакта и категории фото (400 на неизвестное значение)
- **Настройки кафе**: search/favorites/share/labels-переключатели,
  `section_order` (порядок секций страницы), статус
  открыто/закрыто/временно закрыто
- **Дизайн**: пресеты (modern/elegant/minimal/dark/classic/restaurant),
  цвета, радиус карточек — валидация HEX-цвета и пресета
- **Рабочие часы**: частичное обновление (можно передать не все 7 дней),
  режимы workday/day_off/24h
- **Языки**: включение/выключение ru/tg/en для конкретного кафе
- **Tenant isolation на новых ресурсах** — повторно атаковано и подтверждено:
  Admin B получает `404` на GET/PATCH/PUT-attributes/DELETE чужого блюда и
  чужого блока меню; попытка B вставить чужой `dishId` в свой блок молча
  отфильтровывается (пустой список); Admin A получает `400`, если пытается
  привязать блюдо к категории, принадлежащей другому кафе
- В процессе тестирования нашёлся и был исправлен реальный баг: маршрут
  `reorder` для категорий отсутствовал в роутере (был добавлен для блюд/
  блоков/рекламы/галереи/контактов, но не для категорий) — эта система
  честной проверки и нужна именно для отлова таких вещей до продакшена
